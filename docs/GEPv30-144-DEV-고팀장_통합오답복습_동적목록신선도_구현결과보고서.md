# GEPv30-144 통합오답복습 동적목록 신선도 구현 결과보고서

## 1. 재정의된 문제

GEPv30-141에서는 이 항목을 "오답목록 전용 이어풀기 신설"로 정의했으나, `ChallengeMode.jsx` 코드를 실제로 읽어보니 문제의 정체가 달랐다.

`ChallengeMode.jsx`는 문제 목록을 **`getCachedWrongQuestions(userId)`로만 읽고 있었다** — 이 함수는 순수 캐시 조회이며, 캐시가 없으면(만료·최초방문) 즉시 `null`을 반환하고 `pool = []`로 처리된다. `fetchAllWrongQuestions`(실제 조회+캐시)를 호출하는 게 아니었다.

이로 인해 두 가지 문제가 함께 있었다:
1. **캐시가 없을 때(1시간 TTL 만료 등):** 실제로는 틀린 문제가 있어도 "🎉 오답이 없습니다!"라는 잘못된 완료 화면이 뜬다.
2. **캐시가 살아있을 때(1시간 이내 재진입):** 세션 중간에 정답을 맞혀 실제로는 해결된 문제가, 재진입 시 캐시에 박제된 예전 목록 그대로 다시 나타난다 — 이것이 원칙 10("오답목록은 동적으로 재계산되어야 한다")의 실제 위반 지점이었다.

## 2. 설계 판단 — "이어풀기 위치 저장"이 아니라 "항상 최신 조회"

당초 GEPv30-141은 MCQ 서비스B의 ID 앵커 패턴처럼 "마지막 위치를 저장하고 재탐색"하는 방식을 제안했으나, `ChallengeMode`의 문제 목록은 **매번 `attempts` 원장에서 "지금 이 순간 아직 안 풀린 오답"만 다시 계산**하는 자기치유적(self-healing) 구조다. 즉:
- 세션 중 정답을 맞히면 → 다음 조회 시 그 문제는 목록에서 자동으로 빠진다 (last_correct=true)
- 세션 중 또 틀리면 → wrong_count가 1 증가한 채로 계속 남는다

이 구조에서는 "마지막 위치"를 저장할 필요가 없다 — **매번 목록을 새로 가져오기만 하면, 새 목록의 0번부터 시작하는 것 자체가 이미 올바른 재개 지점이다.** 저장된 인덱스/ID가 무의미한 이유는 목록 자체가 매번 다시 계산되기 때문이다. 문제는 "재계산을 안 하고 캐시된 옛 목록을 그대로 썼다"는 데 있었다.

## 3. 수정 내용

| 파일 | 변경 |
|---|---|
| `src/services/unifiedWrongService.js` | `fetchAllWrongQuestions(userId, { bypassCache })` — `bypassCache: true`면 캐시를 건너뛰고 항상 attempts 원장을 새로 조회(다른 화면의 캐시 이점은 유지, 기본값 `false`로 하위호환) |
| `src/pages/ChallengeMode.jsx` | `getCachedWrongQuestions` → `fetchAllWrongQuestions(userId, { bypassCache: true })`로 교체 — 도전 세션을 시작/재개할 때마다 항상 최신 원장 기준 목록을 가져온다 |

## 4. 검증

- `npm run build` — 성공
- 비로그인 스모크: `/unified-wrong/challenge/1` 라우팅 정상, 콘솔에 새로 발생한 에러 없음
- **로그인 상태 실사용 검증은 조대표 본인 브라우저에서 필요** — 도전 모드에서 몇 문제 맞히고 중간에 이탈(뒤로가기/홈) 후 같은 필터로 재진입했을 때, 이미 맞힌 문제가 다시 나오지 않는지 확인 요청
