## 3. 검증 후 보류/추가 조치 필요 (4건)

### 🔴 P-01 — 지시서 전제와 실제 코드 불일치, 미실행

지시서 전제: "직접 UPDATE 호출 없음 확인 후 진행" → **검증 결과 전제가 틀림**.

- `src/services/countingResetService.js:20-22`가 `supabase.from('users').update({ reset_baseline_at })`로 **본인 행을 직접 UPDATE**함 (Settings.jsx "통계 초기화" 기능, GEPv30-104가 사용).
- 운영 DB(`xnmjprtodyonqzsqxxja`) 조회 결과 `users_self_update` 정책 실체:
  ```sql
  FOR UPDATE USING (auth.uid() = user_id) WITH CHECK (auth.uid() = user_id)
  ```
  컬럼 제한이 없는 포괄 정책 — 지적하신 대로 `service_level`/`approval_status` 등 민감 컬럼까지 셀프 에스컬레이션 가능한 취약점 맞음.
- **그대로 DROP하면 통계 초기화 기능이 즉시 깨짐** (RLS가 self-UPDATE 전면 차단).
- 동일 프로젝트 선례 확인: `docs/GEPv30-089`에서 `last_device` 자기 UPDATE도 같은 문제였고, 해법은 정책 삭제가 아니라 SECURITY DEFINER RPC로 화이트리스트 컬럼만 갱신하는 방식이었음(`submit_approval_request`, `update_last_device`와 동일 패턴).

**제안 (승인 대기):**
1. `reset_counting_baseline(p_reason TEXT)` SECURITY DEFINER RPC 신설 — `reset_baseline_at`만 갱신
2. `countingResetService.js`를 RPC 호출로 전환
3. 그 다음 `users_self_update` DROP

이 보완 지시 없이는 A 항목을 실행하지 않음.
