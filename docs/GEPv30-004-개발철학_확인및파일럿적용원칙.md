# GEPv30-004 개발철학 확인 및 파일럿 적용 원칙

## 1. 문서 목적

이 문서는 GEP V3.0 개발을 시작하기 전에 기존 GEP 문서에서 확인한 개발 철학을 다시 정리하고, 2026년 9월부터 진행할 록토코리아 직원 대상 파일럿 서비스에 어떻게 적용할 것인지를 확정하기 위한 기준 문서이다.

V3.0의 개발 철학은 다음 네 가지로 요약한다.

1. 레고블록 방식
2. 탑다운 방식
3. 서비스 시나리오 우선 방식
4. 철저한 기록유지 관리

이 네 가지는 별개의 구호가 아니라 하나의 개발 운영 원칙이다. 먼저 실제 사용자의 서비스 시나리오를 확정하고, 그 시나리오를 탑다운으로 화면과 데이터 구조까지 내린 뒤, 구현은 독립적인 레고블록으로 나누어 진행하며, 모든 의사결정과 사용자 학습 이벤트를 기록으로 남긴다.

## 2. 확인한 기존 문서

이번 확인에 사용한 주요 기존 문서는 다음과 같다.

1. `OLD-DOCS/G020_GEP 개발절차서.md`
2. `OLD-DOCS/G062_탑다운_레고블록_개발철학_세부계획서.md`
3. `OLD-DOCS/G063_사용자시나리오_및_UI_확정_백엔드설계서.md`
4. `OLD-DOCS/G066_문제풀이_UI레고블록_데이터워크플로우_설계서.md`

기존 문서에서 반복적으로 확인되는 핵심은 다음과 같다.

1. 문제 원문 필드는 훼손하지 않는다.
2. 사용자 시나리오와 UI를 먼저 확정하고 백엔드 구조를 설계한다.
3. 기능은 독립적으로 재사용 가능한 레고블록으로 개발한다.
4. 사용자, 문제, 풀이 이벤트, 진행률, 통계는 중앙 구조에서 일관되게 관리한다.
5. 통계는 임의 집계값이 아니라 사용자 이벤트 로그를 기준으로 재계산 가능해야 한다.
6. 하나의 문제 데이터와 하나의 풀이 로직을 여러 서비스에서 재사용한다.
7. 개발 과정과 결정 사항은 문서로 남겨 다음 단계에서 다시 이어받을 수 있어야 한다.

## 3. V3.0 개발 철학

### 3.1 탑다운

V3.0은 먼저 고도화된 전체 서비스의 모습을 정하고, 그중 파일럿 단계에서 필요한 범위만 잘라 구현한다.

이번 파일럿의 최상위 목적은 상용 제품을 바로 출시하는 것이 아니다. 실제 보험중개사 시험 수험생이 2개월 동안 사용하면서 어떤 문제가 있는지 확인하고, 그 피드백을 바탕으로 2027년 상용 제품의 완성도를 높이는 것이다.

따라서 개발 순서는 다음과 같다.

1. 파일럿 사용자 시나리오 확정
2. 서비스 A, 서비스 B, 오답 복습, 등록 승인, 카운팅 초기화 시나리오 확정
3. 화면 흐름 확정
4. 데이터 계약 확정
5. 레고블록 단위 구현
6. 테스트 및 기록

### 3.2 레고블록

V3.0 기능은 다음 블록으로 나누어 개발한다.

1. 회원 등록 및 승인 요청 블록
2. 운영자 승인 및 사용자 관리 블록
3. 서비스 A: 실제 기출문제 순차 풀이 블록
4. 서비스 B: 과목별 10년치 랜덤 풀이 블록
5. 답안 제출 및 정오답 판정 블록
6. 풀이 이벤트 기록 블록
7. 누적 카운팅 및 통계 블록
8. 틀린 문제 다시 풀기 블록
9. 사용자 카운팅 초기화 블록
10. 운영자 카운팅 초기화 블록
11. 파일럿 피드백 수집 블록

각 블록은 독립적으로 테스트 가능해야 하며, 다른 블록과 연결될 때는 명확한 입력과 출력만 주고받아야 한다.

### 3.3 서비스 시나리오 우선

V3.0에서는 기능 이름만으로 개발을 시작하지 않는다. 먼저 실제 사용자가 어떤 순서로 서비스를 이용하는지 문장으로 확정한다.

파일럿의 핵심 시나리오는 다음과 같다.

1. 사용자가 실명과 전화번호를 입력하고 가입 승인을 요청한다.
2. 운영자가 가입 요청을 확인하고 승인한다.
3. 승인된 사용자는 서비스 A 또는 서비스 B를 선택한다.
4. 사용자가 문제를 풀면 즉시 정오답이 표시된다.
5. 동시에 풀이 이벤트가 저장되고 누적 통계가 갱신된다.
6. 사용자는 본인의 현재 위치, 정답률, 취약 과목, 틀린 문제 누적 상태를 확인한다.
7. 사용자는 틀린 문제를 중심으로 다시 풀 수 있다.
8. 사용자가 원하면 설정에서 본인 카운팅을 초기화할 수 있다.
9. 운영자도 필요 시 특정 사용자의 카운팅을 초기화할 수 있다.
10. 초기화 자체도 기록으로 남긴다.

### 3.4 철저한 기록유지 관리

V3.0에서 기록은 두 종류로 나눈다.

첫째, 개발 기록이다. 모든 기획, 설계, 점검, 변경, 테스트, 피드백 문서는 `DOCS` 폴더에 `GEPv30-XXX-파일제목` 형식으로 저장한다. 문서 번호는 개발 흐름을 추적할 수 있도록 순차적으로 부여한다.

둘째, 서비스 기록이다. 승인된 사용자가 문제를 푸는 순간부터 모든 풀이 이벤트는 기록되어야 한다. 정답 여부, 풀이 시각, 문제 ID, 회차, 과목, 선택 답안, 정답, 풀이 모드, 세션 정보가 저장되어야 한다.

통계는 이 기록을 기준으로 계산되어야 하며, 필요한 경우 재계산 가능해야 한다. 카운팅 초기화는 단순 삭제가 아니라 초기화 이벤트 또는 초기화 기준 시점으로 관리하는 방식을 우선 검토한다.

## 4. 파일럿 서비스 적용 원칙

### 4.1 파일럿의 성격

2026년 9월부터 2개월간 록토코리아 직원 중 보험중개사 시험 응시자를 대상으로 제공하는 서비스는 상용 출시 전 검증용 파일럿이다.

이 단계에서는 많은 기능보다 다음 두 가지가 중요하다.

1. 수험생이 실제로 매일 풀 수 있을 만큼 단순할 것
2. 사용자의 모든 풀이 기록과 오답 누적이 정확할 것

따라서 파일럿 1단계는 서비스 A와 서비스 B를 중심으로 구성한다.

### 4.2 서비스 A

서비스 A는 실제 출제되었던 기출문제를 회차와 문제 순서에 따라 제공한다.

핵심 흐름은 다음과 같다.

1. 사용자가 서비스 A를 선택한다.
2. 회차 또는 시작 지점을 선택한다.
3. 실제 출제 순서대로 문제가 제시된다.
4. 사용자가 답을 선택한다.
5. 즉시 정답 또는 오답을 알려준다.
6. 풀이 이벤트와 누적 통계를 저장한다.
7. 다음 문제로 이동한다.

서비스 A는 실전 기출 흐름을 그대로 따라가게 하는 기능이다.

### 4.3 서비스 B

서비스 B는 10년치 기출문제를 과목별로 분류하고, 사용자가 선택한 과목에서 랜덤하게 문제를 제공한다.

핵심 흐름은 다음과 같다.

1. 사용자가 서비스 B를 선택한다.
2. 과목 또는 세부 과목을 선택한다.
3. 해당 과목의 10년치 문제 풀에서 랜덤하게 문제가 제시된다.
4. 사용자가 답을 선택한다.
5. 즉시 정답 또는 오답을 알려준다.
6. 풀이 이벤트와 과목별 통계를 저장한다.
7. 다음 랜덤 문제로 이동한다.

서비스 B는 취약 과목 반복 학습을 위한 기능이다.

### 4.4 틀린 문제 중심 복습

이 서비스의 가장 큰 가치는 사용자가 틀린 문제를 중심으로 다시 풀 수 있다는 점이다.

따라서 오답 복습은 부가기능이 아니라 V3.0의 중심 가치이다. 모든 풀이 이벤트는 오답 누적 횟수를 계산할 수 있어야 하며, 사용자는 본인이 어떤 문제를 몇 번 틀렸는지 확인하고 다시 풀 수 있어야 한다.

오답 복습의 최소 기준은 다음과 같다.

1. 문제별 오답 횟수 저장
2. 문제별 정답 전환 여부 저장
3. 과목별 오답 분포 표시
4. 오답 문제 다시 풀기
5. 다시 맞힌 뒤에도 과거 오답 이력 보존

### 4.5 등록 승인과 카운팅

정밀한 카운팅을 위해 V3.0 파일럿에서는 등록 프로세스를 필수로 둔다.

사용자는 실명과 전화번호를 입력하고 가입 승인 요청을 한다. 운영자가 승인한 시점부터 사용자의 모든 풀이가 카운팅된다.

필수 상태값은 다음과 같다.

1. `pending`: 승인 대기
2. `approved`: 승인 완료, 학습 가능
3. `rejected`: 승인 거절
4. `paused`: 운영자에 의한 일시 중지

승인 전 사용자는 문제 풀이 화면에 진입하지 못하거나, 진입하더라도 기록되지 않는 체험 모드로 제한하는 방식을 별도 검토한다.

### 4.6 카운팅 초기화

카운팅 초기화는 사용자와 운영자 모두 수행할 수 있어야 한다.

다만 초기화는 중요한 학습 기록 변경이므로 다음 원칙을 따른다.

1. 초기화 실행자 기록
2. 초기화 대상 사용자 기록
3. 초기화 시각 기록
4. 초기화 범위 기록
5. 초기화 사유 또는 메모 기록
6. 초기화 전 통계 복원 가능성 검토

파일럿 단계에서는 물리 삭제보다 `reset_event` 또는 `reset_baseline_at` 방식이 더 안전하다. 이 방식은 사용자의 화면에서는 초기화된 것처럼 보이지만, 운영과 검증을 위해 과거 이벤트를 추적할 수 있다.

## 5. 데이터 설계 원칙

V3.0의 통계 기준은 이벤트 로그이다.

최소 데이터 블록은 다음과 같다.

1. `users`: 실명, 전화번호, 승인 상태, 권한, 생성 시각
2. `approval_requests`: 가입 승인 요청과 처리 기록
3. `questions`: 기출문제 원천 데이터
4. `answer_events`: 모든 답안 제출 기록
5. `user_question_stats`: 사용자별 문제 누적 통계
6. `user_subject_stats`: 사용자별 과목 누적 통계
7. `reset_events`: 사용자 또는 운영자의 카운팅 초기화 기록
8. `feedback_events`: 파일럿 사용자 피드백 기록

집계 테이블은 빠른 화면 표시를 위한 파생 데이터로 본다. 최종 진실의 원천은 `answer_events`와 `reset_events`이다.

## 6. 개발 진행 원칙

V3.0 개발에서는 다음 규칙을 지킨다.

1. 시나리오 없는 기능은 개발하지 않는다.
2. 데이터 계약 없는 화면은 개발하지 않는다.
3. 기존 작동 앱의 검증된 흐름은 최대한 계승한다.
4. 문제 원문과 정답 데이터는 직접 수정하지 않고 검증 절차를 거친다.
5. 서비스 A와 서비스 B는 같은 문제 데이터와 같은 답안 제출 로직을 공유한다.
6. 통계는 반드시 이벤트 로그에서 재계산 가능해야 한다.
7. 초기화, 승인, 권한 변경은 모두 기록한다.
8. 개발 문서는 반드시 `DOCS/GEPv30-XXX-파일제목` 형식으로 남긴다.
9. 변경 후에는 빌드 또는 최소 검증을 수행하고 결과를 문서 또는 작업 보고에 남긴다.
10. 파일럿 기간에는 기능 확장보다 실제 수험생 피드백과 카운팅 정확성을 우선한다.

## 7. V3.0 파일럿의 우선순위

1순위는 등록 승인과 정확한 카운팅이다.

2순위는 서비스 A와 서비스 B의 안정적인 문제 제공이다.

3순위는 틀린 문제 중심의 복습 기능이다.

4순위는 사용자에게 현재 위치와 경각심을 주는 통계 화면이다.

5순위는 운영자가 파일럿 사용자의 상태, 기록, 초기화, 피드백을 관리할 수 있는 관리자 기능이다.

## 8. 결론

GEP V3.0은 새로운 앱을 처음부터 만드는 프로젝트가 아니다. 이미 작동 중인 GEP V2.0의 경험과 구조를 계승하면서, 2026년 파일럿 테스트에 맞게 등록 승인, 정밀 카운팅, 오답 중심 복습, 피드백 수집을 우선 고도화하는 프로젝트이다.

개발의 기준 문장은 다음과 같다.

**사용자 시나리오를 먼저 확정하고, 기능은 레고블록으로 나누며, 통계는 이벤트 기록에서 계산하고, 모든 개발 결정은 문서로 남긴다.**
