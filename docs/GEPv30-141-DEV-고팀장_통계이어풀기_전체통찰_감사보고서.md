# GEPv30-141 통계·이어풀기 전체 통찰 감사보고서

**문서 번호:** GEPv30-141 | **작성일:** 2026-08-20 | **작성자:** 고팀장 (Claude Code) | **상태:** 통찰 완료 — 개별 디버깅 우선순위 승인 대기
**선행:** 조대표와의 대화에서 합의된 통계 철학 6원칙 + 보완 5원칙(GEPv30-140 이후 대화, 본 문서 §1에 재정리)
**방법:** 전 서비스(MCQ 서비스A/B, OX, 모의고사, 미니모의고사, 맞춤모의고사, 틀린문제 복습, 통합오답복습)의 실제 코드를 원칙과 직접 대조

---

## 1. 합의된 원칙 (재확인)

### 1-1. 기본 6원칙
1. 카운팅은 부가기능이 아니라 서비스의 중심 엔진 — 사용자가 자기 위치를 깨닫게 하는 것이 목적
2. 원장은 하나(`attempts`) — 모든 통계는 원장에서 재계산 가능해야 함, 캐시는 보조수단
3. 공급 방식(순차/랜덤/OX/모의고사)이 달라도 기록·판정 로직은 하나
4. 통계는 오늘/누적 × 전체/과목별 4축 + 반복오답(맞혀도 이력 보존)
5. 초기화는 삭제가 아니라 기준점 이동
6. 화면은 숫자 나열이 아니라 "당신은 지금 여기 있습니다"를 말해야 함

### 1-2. 대화에서 추가로 확정된 5원칙
7. **문항 수(distinct question) ≠ 시도 횟수(attempt count)** — 같은 문제를 20번 풀면 문항 수는 1, 시도 횟수는 20이며 이 둘을 섞어서 표시하면 안 됨
8. **이어풀기는 기본값** — 명시적으로 "처음부터"를 요청하지 않는 한 항상 마지막 위치부터 재개
9. **이어풀기는 문제 ID 기준이어야 하며, 인덱스(몇 번째) 기준은 위험하다** — 문제 세트 구성이 바뀌면 인덱스가 다른 문제를 가리킬 수 있음
10. **오답목록의 이어풀기는 일반풀이와 다른 로직이 필요** — 목록 자체가 매 조회마다 동적으로 재계산되므로, "마지막으로 다루던 문제 ID가 지금도 목록에 남아있는지"부터 재확인해야 함
11. **정답률은 전체누적과 최근 시도를 구분해야 한다** — 20번 중 16번 정답(80%)이라는 숫자는 "최근에 잘하고 있는지"와 "예전에 틀렸다가 최근에 안정됐는지"를 구분하지 못함. 지금은 `last_correct`(직전 1회 정오답)만 있고 "최근 N회 정답률" 개념 자체가 없음

## 2. 서비스별 통찰 매트릭스

| 서비스 | 기록 스키마 | 이어풀기 구현 상태 | 정답률 계산 방식 | 리스크 |
|---|---|---|---|---|
| MCQ 서비스A(기출순차) | `attempts`(study_mode='service_a_sequence') | **있음.** `examStore.progressMap` + `setCurrentIndex()`가 로컬+Supabase `progress` 양쪽에 인덱스 저장, 로그인 시 `syncProgressFromDB()`가 둘 중 큰 값으로 병합 | 전체누적만(`correct/total`), 최근 N회 없음 | 인덱스 기준이나, 정렬이 `(round, partNumber, id)`로 고정 정렬이라 문제 세트가 바뀌지 않는 한 안전 |
| MCQ 서비스B(과목별랜덤) | 동일, study_mode='service_b_subject_random' | **있음.** 위와 동일 메커니즘 + `questionOrder`(셔플된 문제ID 배열)를 세션에 저장해 인덱스가 항상 같은 ID 순서를 가리키도록 보강되어 있음 — **6개 서비스 중 가장 견고한 이어풀기 설계** | 동일 | 낮음. `orderMatchesPool` 체크로 문제 풀이 바뀌면 재셔플하는 방어도 있음 |
| OX 일반풀기 | `attempts`(study_mode='ox') | **오늘 처음 연결.** `oxService.loadProgress()`가 프로젝트 전체에서 호출되는 곳이 없어(죽은 코드) 이어풀기가 전혀 작동하지 않던 것을 오늘 STEP12에서 연결 — 단, **순수 인덱스 저장 방식이라 MCQ 서비스B의 `questionOrder` 같은 ID 앵커가 없음** | 전체누적만 | **높음.** 원칙 9번(인덱스 위험) 그대로 해당 — 신규 회차 추가나 `조대표_선택` 필터 변경 시 저장된 인덱스가 엉뚱한 문제를 가리킬 수 있음. 재검토 필요 |
| 모의고사 | `mock_exam_sessions`/`mock_exam_attempts` | **있음.** `mockExamStore.resumeExam()`이 세션에서 answers/index/elapsedTime을 복원 | 시험 단위 채점(과목별 점수·합격여부) — 반복오답 개념 자체가 없음(1회성 응시가 원칙이라 4원칙과는 성격이 다름, 별도 설계로 타당) | 낮음. 회차당 120문제 고정, 순서 불변 |
| 미니모의고사 | `miniMockStore`(localStorage 자체 `saveProgress`/`loadProgress`) | 있음(로컬) — **Supabase 동기화 여부 미확인**, 기기 변경 시 유실 가능성 있음 | 세트 단위 채점 | 중간. DB 동기화 여부 개별 디버깅에서 확인 필요 |
| 맞춤모의고사 | `customMockStore`(localStorage 자체 `saveProgress`/`loadProgress`, `sessionLocalId`+`part` 키) | 있음(로컬) — 동일하게 DB 동기화 여부 미확인 | 세트 단위 채점 + 세부과목별 정답률(약점 가중치 로직 있음, `customMockService.js`) | 중간. 동일 |
| 틀린문제 복습(레거시 `WrongReview.jsx`) | `attempts`(study_mode='wrong_review') | **없음.** 매번 재진입 시 처음부터. 원칙 10번(오답목록 전용 이어풀기) 자체가 구현된 적 없음 | 해당 세션 내에서만 카운트, 별도 정답률 없음 | 중간. 다만 L2-D로 유도 배너만 있고 기능 자체는 방치 상태(GEPv30-136 §4 결정5) |
| 통합오답복습(`ChallengeMode.jsx`) | `attempts`(study_mode='unified_wrong_challenge' 또는 원본 모드 유지) | **없음.** 매번 `fetchAllWrongQuestions()`로 목록을 새로 계산해 `currentIndex=0`부터 진행. 세션 중 나갔다 들어오면 처음부터 | 문제별 `wrong_count` 누적(정확), 세션 자체의 정답률 표시는 없음 | 낮음(목록이 매번 새로 계산되므로 "틀린 이력"은 정확하지만, 세션 중 이탈 시 이미 처리한 문제를 또 마주칠 수 있음 — 원칙 10번 미구현) |

## 3. 오늘 나온 버그(D1~D9)를 원칙 위반 관점으로 재분류

| 결함 | 위반 원칙 |
|---|---|
| D2(OX 재도전 채점 오류) | 원칙 2(원장 기준 재계산) — 정답 원본을 조회하지 않고 임의 기본값('O')으로 판정 |
| D3(OX subject 짧은키 저장) | 원칙 3(공급방식 달라도 기록로직 통일) — MCQ·OX가 같은 `attempts`를 쓰면서 값 형식이 다름 |
| D5(OX 재도전 attempts 오염) | 원칙 2, 3 동시 위반 — 기록 자체가 원장 계약을 어김 |
| D6/D7(OX 누적표시 항상 0) | 원칙 7(문항수↔시도수 혼동) 및 원칙 2(세션 캐시를 원장 대신 신뢰) |
| D8(OX 문제원문 미표시) | 원칙 1(서비스 가치) — 사용자가 지문 없이 O/X만 찍는 상태는 서비스 가치 자체를 훼손 |
| D9(OX 이어풀기 죽은 코드) | 원칙 8(이어풀기 기본값) 정면 위반 — 오늘 STEP12로 부분 해결했으나 원칙 9(ID 기준) 관점에서 재검토 필요 |

**즉, 오늘 나온 결함들은 우연이 아니라 지금 합의한 원칙을 하나씩 대입하면 전부 예측 가능했던 위반이었다.**

## 4. 새로 발견된 감사 항목 (오늘 대화 중 발견되지 않았던 것)

1. **정답률에 "최근 N회" 개념이 프로젝트 전체에 없음.** `advancedStatsService.js`, `customMockService.js` 모두 `correct/total` 단순 누적률만 계산. 원칙 11번을 만족하는 곳이 하나도 없음.
2. **MCQ 서비스B의 `questionOrder`(ID 앵커) 패턴이 이미 프로젝트에 존재하는데, 오늘 OX 이어풀기를 만들 때 이 기존 패턴을 참고하지 않고 더 단순한(취약한) 인덱스 방식으로 새로 만들었다.** 이미 있는 좋은 패턴을 재사용하지 못한 것 — 레고블럭 철학 위반이기도 함.
3. **미니모의고사·맞춤모의고사의 진행상태 저장이 로컬(localStorage)에만 있고 Supabase 동기화가 확인되지 않았다.** MCQ(`examStore`)는 이미 DB 동기화가 있는데 이 두 서비스는 아직 검증 안 됨 — 기기 변경 시 진도 유실 가능성.
4. **오답목록(통합오답복습) 이어풀기가 원칙 10번을 아직 만족하지 못한다.** 오늘은 손대지 않은 영역.

## 5. 개별 디버깅 우선순위 제안

원칙 위반 정도와 실사용 영향도를 기준으로 제안한다.

| 우선순위 | 서비스 | 이유 |
|---|---|---|
| 1 | **OX 이어풀기 — 인덱스→ID 앵커 방식으로 재작업** | 오늘 만든 코드가 원칙 9번을 정면으로 위반, MCQ 서비스B의 기존 검증된 패턴(`questionOrder`)을 재사용하면 리스크 없이 바로 교정 가능 |
| 2 | **정답률 "최근 N회" 개념 추가** | 원칙 11번을 만족하는 곳이 프로젝트 전체에 없음 — 설계 결정이 필요한 신규 항목 |
| 3 | **통합오답복습(`ChallengeMode.jsx`) 오답목록 이어풀기** | 원칙 10번 미구현 — 세션 중 이탈 시 재개 로직 신설 필요 |
| 4 | **미니모의고사·맞춤모의고사 DB 동기화 여부 확인** | 검증되지 않은 상태 — 개별 디버깅으로 확인 우선 |
| 5 | **틀린문제 복습(레거시) 이어풀기** | 이미 L2-D로 유도 중인 레거시 화면이라 우선순위 낮음(조대표 기존 결정과 일치) |
