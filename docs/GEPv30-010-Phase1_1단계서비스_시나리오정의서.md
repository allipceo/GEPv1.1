# GEPv30-010 Phase1 1단계 서비스 시나리오정의서

## 1. 문서 목적

이 문서는 GEP V3.0 1단계 파일럿 서비스의 사용자 시나리오를 확정하기 위한 Phase 1 산출물이다.

이 문서가 승인되기 전에는 구현을 시작하지 않는다. 구현은 승인된 시나리오에 포함된 기능만 대상으로 한다.

## 2. 1단계 서비스 정의

1단계 서비스는 2026년 9월부터 2개월간 록토코리아 직원 중 보험중개사 시험 응시자를 대상으로 제공하는 파일럿 서비스이다.

핵심 서비스는 다음 두 가지이다.

1. 서비스 A: 실제 기출문제를 회차와 문제 순서대로 풀기
2. 서비스 B: 10년치 기출문제를 과목별로 랜덤하게 풀기

1단계의 핵심 가치는 문제 제공이 아니라 다음을 사용자가 즉시 알게 하는 것이다.

1. 오늘 얼마나 풀었는가
2. 오늘 어느 과목을 풀었는가
3. 지금까지 얼마나 풀었는가
4. 과목별 정답률은 어떤가
5. 반복해서 틀리는 문제는 무엇인가
6. 시험 전 무엇을 먼저 공부해야 하는가

## 3. 사용자 상태

1단계 서비스의 사용자는 다음 상태 중 하나를 가진다.

1. `guest`: 미등록 또는 미로그인 사용자
2. `pending`: 가입 승인 요청 후 승인 대기 사용자
3. `approved`: 운영자 승인 완료 사용자
4. `rejected`: 승인 거절 사용자
5. `paused`: 운영자가 일시 중지한 사용자

카운팅은 `approved` 상태의 사용자에게만 적용한다.

## 4. 시나리오 1 신규 사용자 가입 승인 요청

### 4.1 시작 조건

사용자가 앱에 처음 접속했거나 아직 승인된 사용자로 확인되지 않은 상태이다.

### 4.2 사용자 행동

1. 사용자가 가입 승인 요청 화면으로 이동한다.
2. 실명을 입력한다.
3. 전화번호를 입력한다.
4. 필요 시 소속 또는 메모를 입력한다.
5. 승인 요청 버튼을 누른다.

### 4.3 시스템 반응

1. 실명과 전화번호의 필수 입력 여부를 확인한다.
2. 전화번호 형식과 중복 요청 여부를 확인한다.
3. 가입 승인 요청을 저장한다.
4. 사용자 상태를 `pending`으로 표시한다.
5. 사용자에게 승인 대기 화면을 보여준다.

### 4.4 저장 데이터

1. 사용자 ID
2. 실명
3. 전화번호
4. 승인 상태: `pending`
5. 요청 시각
6. 요청 메모

### 4.5 종료 조건

사용자는 승인 대기 상태가 되며, 기록되는 문제풀이 서비스에는 진입하지 못한다.

## 5. 시나리오 2 운영자 승인

### 5.1 시작 조건

운영자 화면에 승인 대기 사용자가 존재한다.

### 5.2 운영자 행동

1. 운영자가 승인 대기 사용자 목록을 확인한다.
2. 실명과 전화번호를 확인한다.
3. 승인, 거절, 보류 중 하나를 선택한다.
4. 필요 시 운영자 메모를 입력한다.

### 5.3 시스템 반응

1. 승인 시 사용자 상태를 `approved`로 변경한다.
2. 거절 시 사용자 상태를 `rejected`로 변경한다.
3. 보류 시 사용자 상태를 `pending`으로 유지한다.
4. 승인 처리자, 처리 시각, 처리 메모를 저장한다.

### 5.4 저장 데이터

1. 대상 사용자 ID
2. 이전 상태
3. 변경 상태
4. 처리자
5. 처리 시각
6. 처리 메모

### 5.5 종료 조건

승인된 사용자는 서비스 A와 서비스 B에 진입할 수 있다.

## 6. 시나리오 3 승인 사용자 서비스 진입

### 6.1 시작 조건

사용자 상태가 `approved`이다.

### 6.2 사용자 행동

1. 사용자가 앱 홈에 접속한다.
2. 서비스 A 또는 서비스 B를 선택한다.

### 6.3 시스템 반응

1. 사용자 승인 상태를 확인한다.
2. 승인 상태가 `approved`이면 선택한 서비스로 이동한다.
3. 승인 상태가 아니면 승인 대기 또는 접근 제한 화면을 보여준다.

### 6.4 저장 데이터

서비스 진입 자체는 필수 카운팅 이벤트가 아니다. 단, 필요 시 파일럿 분석을 위해 진입 로그를 별도 기록할 수 있다.

### 6.5 종료 조건

사용자가 선택한 문제풀이 서비스 화면으로 이동한다.

## 7. 시나리오 4 서비스 A 실제 기출 순차 풀이

### 7.1 시작 조건

사용자가 `approved` 상태이고 서비스 A를 선택했다.

### 7.2 사용자 행동

1. 회차를 선택한다.
2. 시작 또는 이어풀기를 선택한다.
3. 실제 출제 순서대로 제시되는 문제를 읽는다.
4. 답안을 선택한다.
5. 정오답을 확인한다.
6. 다음 문제로 이동한다.

### 7.3 시스템 반응

1. 선택 회차의 문제를 실제 출제 순서대로 불러온다.
2. 사용자가 답을 선택하면 정답과 비교한다.
3. 정답 또는 오답을 즉시 표시한다.
4. 답안 제출 이벤트를 저장한다.
5. 오늘 통계와 누적 통계의 원천 이벤트가 생성된다.
6. 이어풀기 위치를 저장한다.

### 7.4 저장 데이터

1. 사용자 ID
2. 문제 ID
3. 회차
4. 과목
5. 세부 과목
6. 서비스 모드: `service_a_sequence`
7. 선택 답안
8. 정답
9. 정오답 여부
10. 풀이 시각
11. 세션 ID

### 7.5 종료 조건

문제 풀이 이벤트가 저장되고 다음 문제로 이동할 수 있다.

## 8. 시나리오 5 서비스 B 과목별 랜덤 풀이

### 8.1 시작 조건

사용자가 `approved` 상태이고 서비스 B를 선택했다.

### 8.2 사용자 행동

1. 과목 또는 세부 과목을 선택한다.
2. 랜덤으로 제시되는 문제를 읽는다.
3. 답안을 선택한다.
4. 정오답을 확인한다.
5. 다음 랜덤 문제로 이동한다.

### 8.3 시스템 반응

1. 선택한 과목 또는 세부 과목의 10년치 문제 풀을 구성한다.
2. 문제 풀 안에서 랜덤으로 문제를 제시한다.
3. 사용자가 답을 선택하면 정답과 비교한다.
4. 정답 또는 오답을 즉시 표시한다.
5. 답안 제출 이벤트를 저장한다.
6. 과목별 통계의 원천 이벤트가 생성된다.

### 8.4 저장 데이터

1. 사용자 ID
2. 문제 ID
3. 회차
4. 과목
5. 세부 과목
6. 서비스 모드: `service_b_subject_random`
7. 선택 답안
8. 정답
9. 정오답 여부
10. 풀이 시각
11. 세션 ID

### 8.5 종료 조건

문제 풀이 이벤트가 저장되고 다음 랜덤 문제로 이동할 수 있다.

## 9. 시나리오 6 답안 제출과 카운팅

### 9.1 시작 조건

승인 사용자가 서비스 A 또는 서비스 B에서 문제를 보고 있다.

### 9.2 사용자 행동

사용자가 답안 버튼을 누른다.

### 9.3 시스템 반응

1. 현재 문제의 정답과 사용자 선택 답안을 비교한다.
2. 정답 또는 오답을 표시한다.
3. 답안 제출 이벤트를 저장한다.
4. 오늘 전체 통계를 갱신할 수 있게 한다.
5. 오늘 과목별 통계를 갱신할 수 있게 한다.
6. 누적 전체 통계를 갱신할 수 있게 한다.
7. 누적 과목별 통계를 갱신할 수 있게 한다.
8. 오답이면 문제별 오답 횟수에 반영한다.

### 9.4 중복 제출 기준

같은 화면에서 같은 문제를 반복 클릭해도 기본 카운팅은 1회만 인정한다.

다만 사용자가 별도 복습 세션에서 같은 문제를 다시 풀면 새로운 풀이 이벤트로 저장한다.

### 9.5 저장 데이터

답안 제출 이벤트는 V3.0 카운팅의 최종 원장이다.

필수 저장값은 다음과 같다.

1. 사용자 ID
2. 문제 ID
3. 서비스 모드
4. 회차
5. 과목
6. 세부 과목
7. 선택 답안
8. 정답
9. 정오답 여부
10. 풀이 시각
11. 세션 ID
12. 초기화 기준 적용 여부

## 10. 시나리오 7 오늘 통계 확인

### 10.1 시작 조건

승인 사용자가 오늘 1문제 이상 풀이했다.

### 10.2 사용자 질문

사용자는 다음 질문에 답을 얻고자 한다.

1. 오늘 총 몇 문제를 풀었는가?
2. 오늘 몇 문제를 맞혔는가?
3. 오늘 정답률은 몇 퍼센트인가?
4. 오늘 어떤 과목을 풀었는가?
5. 오늘 과목별 정답률은 얼마인가?

### 10.3 시스템 반응

1. 오늘 전체 풀이 수를 표시한다.
2. 오늘 전체 정답 수와 오답 수를 표시한다.
3. 오늘 전체 정답률을 표시한다.
4. 오늘 과목별 풀이 수를 표시한다.
5. 오늘 과목별 정답률을 표시한다.

### 10.4 계산 기준

오늘 통계는 사용자의 `reset_baseline_at` 이후, 오늘 날짜에 해당하는 답안 제출 이벤트를 기준으로 계산한다.

## 11. 시나리오 8 누적 통계 확인

### 11.1 시작 조건

승인 사용자가 앱에서 문제를 풀이한 이력이 있다.

### 11.2 사용자 질문

사용자는 다음 질문에 답을 얻고자 한다.

1. 앱 시작 후 지금까지 총 몇 문제를 풀었는가?
2. 누적 정답률은 얼마인가?
3. 과목별로 지금까지 몇 문제를 풀었는가?
4. 과목별 누적 정답률은 얼마인가?
5. 가장 취약한 과목은 무엇인가?

### 11.3 시스템 반응

1. 누적 전체 풀이 수를 표시한다.
2. 누적 정답 수와 오답 수를 표시한다.
3. 누적 전체 정답률을 표시한다.
4. 누적 과목별 풀이 수와 정답률을 표시한다.
5. 취약 과목을 표시한다.

### 11.4 계산 기준

누적 통계는 사용자의 `reset_baseline_at` 이후 모든 답안 제출 이벤트를 기준으로 계산한다.

## 12. 시나리오 9 반복 오답 확인

### 12.1 시작 조건

승인 사용자가 같은 문제를 1회 이상 틀린 기록이 있다.

### 12.2 사용자 질문

사용자는 다음 질문에 답을 얻고자 한다.

1. 내가 2번 이상 틀린 문제는 몇 개인가?
2. 내가 3번 이상 틀린 문제는 몇 개인가?
3. 내가 4번 이상 틀린 문제는 몇 개인가?
4. 반복 오답 문제가 어느 과목에 몰려 있는가?

### 12.3 시스템 반응

1. 2회 이상 오답 문제 수를 표시한다.
2. 3회 이상 오답 문제 수를 표시한다.
3. 4회 이상 오답 문제 수를 표시한다.
4. 과목별 반복 오답 분포를 표시한다.
5. N회 이상 오답 문제 다시 풀기 진입점을 제공한다.

### 12.4 계산 기준

반복 오답은 문제별 오답 횟수를 기준으로 계산한다.

사용자가 나중에 같은 문제를 맞혔더라도 과거 오답 횟수 자체는 사라지지 않는다.

## 13. 시나리오 10 N회 이상 오답 다시 풀기

### 13.1 시작 조건

승인 사용자에게 N회 이상 틀린 문제가 존재한다.

### 13.2 사용자 행동

1. 사용자가 오답 기준 횟수를 선택한다.
2. 필요 시 과목을 선택한다.
3. N회 이상 틀린 문제 목록에서 문제를 다시 푼다.

### 13.3 시스템 반응

1. N회 이상 틀린 문제만 필터링한다.
2. 과목이 선택되어 있으면 해당 과목 안에서만 필터링한다.
3. 오답 횟수가 높은 문제를 우선 제시한다.
4. 사용자가 답을 제출하면 새로운 답안 제출 이벤트를 저장한다.
5. 다시 틀리면 반복 오답 횟수가 증가한다.
6. 다시 맞혀도 과거 반복 오답 이력은 보존한다.

### 13.4 예시

1. 전체 과목에서 4회 이상 틀린 문제 다시 풀기
2. 해상보험에서 4회 이상 틀린 문제 다시 풀기
3. 보험업법에서 3회 이상 틀린 문제 다시 풀기
4. 전체 과목에서 5회 이상 틀린 문제 랜덤 다시 풀기

## 14. 시나리오 11 사용자 카운팅 초기화

### 14.1 시작 조건

승인 사용자가 설정 화면에서 카운팅 초기화를 선택한다.

### 14.2 사용자 행동

1. 사용자가 카운팅 초기화 버튼을 누른다.
2. 시스템 안내를 확인한다.
3. 초기화를 확정한다.

### 14.3 시스템 반응

1. 초기화 실행자를 사용자 본인으로 기록한다.
2. 초기화 시각을 기록한다.
3. 초기화 기준 시점을 갱신한다.
4. 사용자 화면의 통계는 초기화 이후 기록만 기준으로 표시한다.
5. 과거 답안 이벤트는 삭제하지 않는다.

### 14.4 저장 데이터

1. 사용자 ID
2. 실행자 ID
3. 실행자 유형: `self`
4. 초기화 시각
5. 초기화 범위
6. 초기화 전 기준 시점
7. 초기화 후 기준 시점

## 15. 시나리오 12 운영자 카운팅 초기화

### 15.1 시작 조건

운영자가 특정 사용자의 기록을 확인하고 있다.

### 15.2 운영자 행동

1. 운영자가 특정 사용자를 선택한다.
2. 카운팅 초기화를 선택한다.
3. 초기화 사유를 입력한다.
4. 초기화를 확정한다.

### 15.3 시스템 반응

1. 초기화 실행자를 운영자로 기록한다.
2. 대상 사용자를 기록한다.
3. 초기화 시각과 사유를 저장한다.
4. 대상 사용자의 통계 기준 시점을 갱신한다.
5. 과거 답안 이벤트는 삭제하지 않는다.

### 15.4 저장 데이터

1. 대상 사용자 ID
2. 운영자 ID
3. 실행자 유형: `operator`
4. 초기화 시각
5. 초기화 범위
6. 초기화 사유
7. 초기화 전 기준 시점
8. 초기화 후 기준 시점

## 16. 1단계 제외 시나리오

다음은 1단계에서 제외한다.

1. 결제
2. AI 추천
3. 고급 합격 예측
4. 복잡한 차트
5. 다중 회사 또는 다중 조직 관리
6. 자동 문자 발송
7. 문제 해설 자동 생성
8. 시험장 모드 전체 구현

단, 반복 오답과 시험 임박 학습 모드를 나중에 확장할 수 있도록 데이터 구조는 열어둔다.

## 17. Phase 1 게이트웨이 점검 항목

Phase 1 게이트웨이에서 확인할 항목은 다음과 같다.

1. 대표님이 서비스 A와 서비스 B의 흐름을 승인하는가?
2. 승인 사용자만 카운팅한다는 원칙이 명확한가?
3. 답안 제출 1건의 저장 의미가 명확한가?
4. 오늘 통계와 누적 통계의 사용자 질문이 명확한가?
5. 반복 오답과 N회 이상 다시 풀기 흐름이 명확한가?
6. 카운팅 초기화가 삭제가 아니라 기준 시점 변경이라는 원칙이 명확한가?
7. 1단계 제외 기능이 명확한가?

## 18. 채팀장 판단

Phase 1 시나리오는 V3.0 1단계 개발을 시작하기에 충분한 수준으로 정리되었다.

다만 다음 사항은 대표님 승인 또는 수정 지시가 필요하다.

1. 미승인 사용자는 문제풀이 자체를 막을지, 체험 풀이만 허용할지
2. 서비스 A에서 회차 선택을 허용할지, 10년치 전체 순차 흐름으로 갈지
3. 서비스 B에서 과목만 선택할지, 세부 과목까지 선택하게 할지
4. 반복 오답에서 정답 처리된 문제를 목록에서 숨길지, 이력 보존 상태로 계속 보여줄지
5. 운영자 화면의 최소 범위를 승인 관리까지만 둘지, 사용자 통계 확인까지 포함할지

이 다섯 가지가 확정되면 Phase 2 데이터와 카운팅 계약으로 넘어갈 수 있다.
