# GEPv30-005 1단계 서비스 개발절차 채팀장 건의안

## 1. 건의 요지

이번 GEP V3.0 1단계 서비스는 이미 작동 중인 GEP V2.0 앱과 완성된 DB, 백엔드를 기반으로 한다. 따라서 새로운 기술 실험이나 대규모 재설계가 아니라, 파일럿 수험생이 실제로 사용할 수 있는 핵심 흐름을 빠르게 안정화하는 방식이 가장 적합하다.

채팀장 입장에서 권하는 방식은 다음과 같다.

**서비스 시나리오는 엄격하게 통제하고, 구현 세부는 레고블록 단위로 유연하게 진행하며, 단계별 게이트웨이에서는 레드팀 관점으로 통과 여부를 판단한다.**

너무 세부적으로 통제하면 진도가 느려지고, 너무 융통성을 주면 방향이 흐려진다. 따라서 통제 대상은 코드 작성 방식이 아니라 다음 네 가지로 한정하는 것이 좋다.

1. 사용자가 실제로 경험하는 서비스 시나리오
2. 사용자의 풀이 이벤트가 정확히 기록되는지 여부
3. 오답 누적과 다시 풀기가 정확히 작동하는지 여부
4. 운영자가 승인과 초기화를 통제할 수 있는지 여부

## 2. 1단계 서비스의 범위

1단계 서비스는 2026년 9월 파일럿 테스트를 위한 기초 서비스이다.

포함 범위는 다음으로 제한한다.

1. 실명과 전화번호 기반 가입 승인 요청
2. 운영자 승인
3. 서비스 A: 실제 기출문제 순차 제공
4. 서비스 B: 과목별 10년치 랜덤 제공
5. 답안 제출 후 정오답 표시
6. 사용자별 풀이 이벤트 저장
7. 사용자별 누적 카운팅
8. 틀린 문제 다시 풀기
9. 사용자 또는 운영자에 의한 카운팅 초기화
10. 기본 관리자 확인 화면

1단계에서 제외할 항목은 다음과 같다.

1. 결제
2. AI 추천
3. 고급 리포트
4. 복잡한 차트
5. 자동 마케팅 기능
6. 다중 조직 관리
7. 과도한 UI 개편

## 3. 권장 개발 절차

### Phase 0. 기준선 확정

목표는 현재 작동 앱과 DB, 백엔드의 기준선을 확정하는 것이다.

작업 내용은 다음과 같다.

1. 현재 배포 앱과 GitHub 원천 저장소 일치 여부 확인
2. 현재 DB 테이블과 카운팅 로직 확인
3. 현재 앱에서 재사용할 화면과 로직 표시
4. 31회 포함 여부와 10년치 데이터 범위 확인
5. 파일럿 1단계에서 건드리지 않을 기능 목록 확정

게이트웨이 통과 기준은 다음과 같다.

1. 현재 앱이 로컬에서 빌드된다.
2. 문제 데이터 범위가 확인된다.
3. 기존 카운팅 구조의 재사용 가능 여부가 확인된다.
4. 변경 금지 영역이 문서화된다.

### Phase 1. 서비스 시나리오 확정

목표는 개발자가 해석할 여지가 없을 정도로 1단계 사용자 흐름을 확정하는 것이다.

확정할 시나리오는 다음과 같다.

1. 신규 사용자가 가입 승인 요청을 하는 흐름
2. 운영자가 사용자를 승인하는 흐름
3. 승인된 사용자가 서비스 A를 푸는 흐름
4. 승인된 사용자가 서비스 B를 푸는 흐름
5. 사용자가 틀린 문제를 다시 푸는 흐름
6. 사용자가 본인 카운팅을 초기화하는 흐름
7. 운영자가 특정 사용자의 카운팅을 초기화하는 흐름

게이트웨이 통과 기준은 다음과 같다.

1. 각 시나리오가 시작 조건, 사용자 행동, 시스템 반응, 저장 데이터, 종료 조건을 가진다.
2. 시나리오에 없는 기능은 1단계 개발 대상에서 제외된다.
3. 대표님이 시나리오 문서를 승인한다.

### Phase 2. 데이터 계약 확정

목표는 화면보다 먼저 기록 구조를 확정하는 것이다.

확정할 데이터 계약은 다음과 같다.

1. 사용자 식별 기준
2. 승인 상태값
3. 답안 제출 이벤트 필드
4. 정오답 판정 기준
5. 오답 횟수 계산 기준
6. 초기화 처리 방식
7. 운영자 조작 기록 방식

게이트웨이 통과 기준은 다음과 같다.

1. 답안 제출 1건이 어떤 테이블에 어떤 값으로 저장되는지 명확하다.
2. 통계가 이벤트 로그에서 재계산 가능하다.
3. 초기화가 단순 삭제가 아니라 기록 가능한 방식으로 설계된다.
4. 기존 DB와 충돌하지 않는다.

### Phase 3. 레고블록 구현

목표는 한 번에 전체 서비스를 만들지 않고, 독립 블록을 순서대로 붙이는 것이다.

권장 구현 순서는 다음과 같다.

1. 가입 승인 블록
2. 승인 사용자 접근 제어 블록
3. 공통 답안 제출 및 이벤트 기록 블록
4. 서비스 A 문제 공급 블록
5. 서비스 B 문제 공급 블록
6. 정오답 피드백 블록
7. 누적 카운팅 블록
8. 오답 복습 블록
9. 카운팅 초기화 블록
10. 운영자 확인 블록

게이트웨이 통과 기준은 다음과 같다.

1. 각 블록은 독립 테스트가 가능하다.
2. 서비스 A와 B가 같은 답안 제출 로직을 사용한다.
3. 통계가 화면 표시값과 DB 기록 사이에서 일치한다.
4. 기존 정상 기능을 깨지 않는다.

### Phase 4. 레드팀 점검

목표는 사용자의 입장이 아니라 감독관의 입장에서 서비스 실패 가능성을 찾는 것이다.

레드팀 점검 질문은 다음과 같다.

1. 승인되지 않은 사용자가 문제를 풀고 기록을 만들 수 있는가?
2. 같은 문제를 여러 번 풀었을 때 카운팅이 의도대로 누적되는가?
3. 서비스 A와 서비스 B에서 같은 문제가 풀렸을 때 통계가 일관되는가?
4. 오답이었다가 정답이 된 문제의 이력이 사라지지 않는가?
5. 초기화 후 사용자 화면과 운영자 기록이 서로 모순되지 않는가?
6. 새로고침, 뒤로가기, 중복 클릭으로 카운팅이 틀어지는가?
7. 모바일 화면에서 답안 제출과 피드백이 명확한가?
8. 2개월 파일럿 후 피드백을 분석할 기록이 남는가?

게이트웨이 통과 기준은 다음과 같다.

1. 치명 오류가 없다.
2. 카운팅 오류가 없다.
3. 승인과 초기화 기록이 남는다.
4. 사용자 시나리오 전체가 모바일과 웹에서 통과된다.

### Phase 5. 파일럿 릴리스

목표는 록토코리아 직원이 실제 공부에 사용할 수 있는 안정 버전을 배포하는 것이다.

릴리스 전 확인 사항은 다음과 같다.

1. 테스트 계정 승인
2. 서비스 A 정상 풀이
3. 서비스 B 정상 풀이
4. 오답 복습 정상 동작
5. 카운팅 초기화 정상 동작
6. 운영자 화면 정상 동작
7. 모바일 화면 확인
8. 파일럿 피드백 수집 방식 확인

릴리스 후에는 매주 1회 다음 기록을 확인한다.

1. 사용자별 풀이 문제 수
2. 사용자별 정답률
3. 사용자별 오답 누적 문제
4. 과목별 취약도
5. 이탈 지점
6. 사용자 피드백
7. 오류 또는 불편 신고

## 4. 20분 룰

대표님의 방침에 따라 20분 룰을 적용한다.

적용 대상은 다음과 같다.

1. 원인을 알 수 없는 빌드 실패
2. DB 기록 불일치
3. 카운팅 불일치
4. 승인 상태 오류
5. 초기화 오류
6. 배포 후 재현 가능한 사용자 오류

운영 방식은 다음과 같다.

1. 같은 문제를 20분 이상 해결하지 못하면 작업을 중단한다.
2. 중단 시점의 증상, 시도한 조치, 로그, 의심 원인을 문서화한다.
3. 대표님에게 보고한다.
4. 대표님이 필요 시 외부 기술자문을 동원한다.
5. 해결 후 원인과 조치 결과를 `DOCS`에 남긴다.

20분 룰은 개발자를 압박하기 위한 규칙이 아니라, 막힌 문제에 시간을 낭비하지 않고 프로젝트 속도를 유지하기 위한 안전장치이다.

## 5. 채팀장 권고

이번 1단계는 어렵게 만들 필요가 없다. 이미 DB와 백엔드가 완성되어 있고, 기존 앱도 작동하고 있다. 따라서 가장 위험한 것은 기술 난이도가 아니라 범위 확장과 카운팅 불일치이다.

채팀장으로서 권하는 운영 방식은 다음과 같다.

1. 대표님은 시나리오와 게이트웨이 승인에 집중한다.
2. 채팀장은 구현 세부와 테스트를 책임진다.
3. 레드팀 점검은 각 Phase 종료 시에만 강하게 수행한다.
4. Phase 중간의 작은 구현 선택은 채팀장이 기존 구조에 맞춰 판단한다.
5. 카운팅, 승인, 초기화, 오답 복습에 관한 변경은 반드시 보고하고 기록한다.
6. 20분 이상 막힌 기술 문제는 즉시 중단하고 대표님에게 보고한다.

## 6. 결론

GEP V3.0 1단계 서비스의 최적 개발 방식은 다음 한 문장으로 정리된다.

**시나리오는 대표님이 승인하고, 구현은 채팀장이 레고블록으로 빠르게 진행하며, 각 Phase의 게이트웨이에서 레드팀 관점으로 카운팅과 사용자 흐름을 검증한다.**

이 방식이면 통제력과 속도를 동시에 확보할 수 있다.
