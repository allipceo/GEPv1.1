이 문서는 GEP V3.0 1단계 개발의 Phase 0 기준선 점검 결과를 기록한다.

## 7. 기존 DB/백엔드 구조

저장소 안의 `supabase/schema.sql`과 마이그레이션 파일을 기준으로 확인한 핵심 테이블은 다음과 같다.

1. `users`: 사용자 원장, `status`, `service_level` 보유
2. `attempts`: 객관식 및 OX 풀이 이벤트 원장
3. `question_stats`: 문제별 집계 캐시
4. `progress`: 이어풀기 진행 상태
5. `mock_exam_sessions`: 모의고사 세션
6. `mock_exam_attempts`: 모의고사 문제별 응답 원장
7. `custom_mock_sessions`: 맞춤 모의고사 세션
8. `custom_mock_attempts`: 맞춤 모의고사 문제별 응답 원장
9. `wrong_questions`: MCQ 오답 빠른 조회용
10. `ox_wrong_questions`: OX 오답 빠른 조회용

확인한 RPC는 다음과 같다.

1. `upsert_question_stat`
2. `increment_wrong_count_mcq`
3. `increment_wrong_count_ox`

단, 실제 Supabase 운영 DB의 현재 상태는 로컬 SQL 파일과 코드 기준으로 추정한 것이다. 운영 DB 직접 접속 검증은 Phase 2 또는 구현 직전 별도 확인이 필요하다.

## 8. 기존 카운팅 자산

현재 앱에는 다음 카운팅 자산이 이미 존재한다.

### 8.1 기본 MCQ 카운팅

`statsService.js`의 `recordAttempt`는 다음을 수행한다.

1. 로컬 `statsStore` 업데이트
2. 인증 사용자이고 통계 권한이 있으면 `attempts` 테이블에 풀이 이벤트 저장
3. `upsert_question_stat` RPC로 문제별 집계 캐시 갱신

현재 `attempts`에 저장되는 주요 필드는 다음과 같다.

1. `user_id`
2. `question_id`
3. `question_round`
4. `subject`
5. `sub_subject`
6. `study_mode`
7. `selected_answer`
8. `is_correct`
9. `exam_version`
10. `service_level`
11. `attempted_at`

이는 V3.0에서 요구하는 이벤트 기반 카운팅의 핵심 원장으로 재사용 가능하다.

### 8.2 로컬 통계

`statsStore.js`는 로컬 저장소 `gep_stats_v1`을 사용하여 다음 통계를 보유한다.

1. 전체 풀이 수와 정답 수
2. 일자별 풀이 수와 정답 수
3. 과목별 풀이 수와 정답 수
4. 회차별 풀이 수와 정답 수

다만 V3.0 파일럿의 정식 카운팅은 로컬 저장소가 아니라 승인 사용자 기준 Supabase 이벤트 원장을 기준으로 해야 한다.

### 8.3 통합 오답 자산

`unifiedWrongService.js`에는 다음 기능이 있다.

1. MCQ, OX, 모의고사, 맞춤 모의고사 오답 병합 조회
2. `wrong_count` 기준 내림차순 정렬
3. 1회, 2회, 3회, 4회, 5회, 6회 이상 오답 분포 계산
4. N회 이상 오답 필터
5. 오답 복습 후 정답이면 오답 목록에서 제거, 오답이면 `wrong_count + 1`

이는 대표님이 강조한 “많이 틀린 문제순 시험 임박 학습”의 핵심 자산으로 재사용 가능하다.

## 9. 현재 기준선의 빈칸

V3.0 1단계 요구사항 대비 현재 기준선에서 보강이 필요한 부분은 다음과 같다.

### 9.1 실명과 전화번호 기반 가입 승인

현재 `authStore`는 Google OAuth와 `users.service_level` 중심으로 동작한다.

V3.0 파일럿 요구사항인 실명, 전화번호 입력, 승인 요청, 운영자 승인 상태는 별도 구현 또는 `users` 확장이 필요하다.

필요한 보강 후보는 다음과 같다.

1. 실명 필드
2. 전화번호 필드
3. 승인 상태
4. 승인 요청 시각
5. 승인 처리자
6. 승인 처리 시각
7. 승인 메모

### 9.2 승인 사용자만 카운팅

현재는 `authStatus === authenticated`와 `serviceLevel` 기준으로 Supabase 저장 여부가 결정된다.

V3.0 파일럿에서는 `approved` 사용자만 카운팅되어야 하므로 승인 상태 기반 접근 제어가 필요하다.

### 9.3 카운팅 초기화 기록

현재 `statsStore.resetStats`는 로컬 통계를 삭제하고 기본값으로 복원한다.

V3.0 파일럿 요구사항은 사용자 또는 운영자가 초기화할 수 있으면서도 초기화 자체가 기록으로 남는 구조이다.

따라서 다음 중 하나가 필요하다.

1. `reset_events` 테이블 신설
2. `users.reset_baseline_at` 필드 추가
3. 둘을 함께 사용

권장 방향은 `reset_events`와 `reset_baseline_at`을 함께 사용하는 것이다.

### 9.4 서비스 A/B 명명과 단순화

현재 `/question`은 회차, 과목, 세부과목 필터 기반 문제풀이로 동작한다.

V3.0 파일럿에서는 사용자가 이해하기 쉽게 다음으로 분리하는 것이 좋다.

1. 서비스 A: 회차별 실제 순서 기출 풀이
2. 서비스 B: 과목별 랜덤 기출 풀이

내부 로직은 기존 문제풀이와 카운팅 로직을 최대한 재사용한다.

## 13. Phase 0 게이트웨이 판단

Phase 0의 게이트웨이 결론은 **조건부 통과**이다.

통과 근거는 다음과 같다.

1. 로컬 빌드가 성공했다.
2. 23회부터 31회까지 1,080문항의 객관식 데이터가 확인되었다.
3. 31회 120문항과 정답 누락 0건이 확인되었다.
4. OX 3,824문항 데이터가 확인되었다.
5. `attempts` 기반 풀이 이벤트 원장이 존재한다.
6. `question_stats`와 `wrong_count` 기반 오답 자산이 존재한다.
7. 서비스 A/B 구현에 필요한 기존 문제풀이 화면과 로직을 재사용할 수 있다.

조건부 통과 사유는 다음과 같다.

1. 실명과 전화번호 기반 승인 프로세스는 신규 보강이 필요하다.
2. 승인 상태 기반 카운팅 조건은 신규 보강이 필요하다.
3. 기록 보존형 카운팅 초기화는 신규 보강이 필요하다.
4. 운영 DB의 실제 스키마 상태는 구현 전 재확인이 필요하다.
5. 의존성 취약점은 파일럿 배포 전 보강해야 한다.

따라서 Phase 1 서비스 시나리오 확정으로 이동할 수 있다. 단, Phase 1과 Phase 2에서 승인 상태, 카운팅 조건, 초기화 기록 방식을 반드시 명확히 확정해야 한다.
