## 1. 검증 시나리오 (지시서 원문)

> 서비스 B에서 세부과목 문제 풀기 중
> 10번 문제 제출(오답) → 이전 버튼으로 9번 이동 → 9번 제출 → 다시 10번 이동 → 10번 재제출
> → Supabase attempts 테이블에 10번 문제가 2개 row로 기록되는가?

---

## 2. 관련 코드 — `src/pages/Question.jsx`

```javascript
const [recordedSet, setRecordedSet] = useState(new Set())   // 컴포넌트 로컬 state (세션 단위)

const handleAnswer = async (num) => {
  saveAnswer(question.id, num)                               // ① 항상 실행 — 표시용 답안 갱신
  setLocalAnswered((prev) => new Set([...prev, question.id]))

  if (recordedSet.has(question.id)) return                   // ② 이미 기록된 문제면 여기서 중단

  await recordAttempt(useStatsStore.getState(), authState, { question, selectedAnswer: num, isCorrect: ... })
  setRecordedSet((prev) => new Set([...prev, question.id]))  // ③ 기록 후에만 recordedSet에 추가
}

const handlePrev = () => {
  const prevId = filteredQuestions[currentIndex - 1]?.id
  if (prevId) setLocalAnswered((prev) => { const next = new Set(prev); next.delete(prevId); return next })
  setCurrentIndex(currentIndex - 1)                           // recordedSet은 건드리지 않음
}
```

핵심: `recordedSet`은 `이전`/`다음` 이동으로는 절대 초기화되지 않는다. Question.jsx 컴포넌트가 **마운트된 상태로 유지되는 한** 계속 누적된다. 초기화되는 시점은 컴포넌트가 언마운트될 때(예: `/result`로 이동, 홈으로 나갔다가 서비스A/B에 다시 진입) 뿐이다.

## 3. 시나리오 단계별 추적

| 단계 | 동작 | `recordedSet` 상태 | attempts INSERT 발생? |
|---|---|---|---|
| 1 | 10번 제출(오답) | `{}` → `{10}` | ✅ 1건 발생 (10번, is_correct=false) |
| 2 | 이전 버튼 → 9번 이동 | `{10}` (불변) | — (제출 아님) |
| 3 | 9번 제출 | `{10}` → `{10, 9}` (9번이 이 세션에서 처음 제출이라는 전제) | ✅ 1건 발생 (9번) |
| 4 | 다음 버튼 → 10번 이동 | `{10, 9}` (불변) | — (제출 아님) |
| 5 | 10번 재제출 | `recordedSet.has(10)` → **true** → `handleAnswer` 2번째 줄에서 `return` | ❌ **발생 안 함** |

## 4. 결론

**attempts 테이블에 10번 문제가 2개 row로 기록되지 않는다.** `recordedSet` 가드가 정확히 이 케이스를 차단한다 — 같은 세션(컴포넌트 마운트) 안에서는 같은 문제에 대해 최초 1회만 `attempts`에 INSERT된다. 이는 [GEPv30-012 카운팅 계약](../DOCS/GEPv30-012-Phase2_데이터카운팅계약_정의서.md) 4.3절 5항("같은 화면에서 중복 클릭된 답안은 중복 저장하지 않는다")과 정확히 일치하는 동작이며, **계약 위반이 아니다.**

## 5. 그러나 발견한 부수 효과 — GEPv30-012 계약이 다루지 않는 지점

5단계에서 `saveAnswer(question.id, num)`(코드 ①)는 `recordedSet` 가드와 무관하게 **항상 실행된다.** 즉:

- 화면에 표시되는 10번의 "선택한 답"은 **마지막 제출값**(5단계에서 새로 고른 답)으로 갱신된다.
- 그러나 `attempts` 테이블과 그로부터 계산되는 `is_correct`·통계(`question_stats`, `statsStore.bySubject` 등)는 **최초 제출값**(1단계)에 고정된 채로 남는다.

**구체적으로:** 사용자가 10번을 처음엔 오답으로 냈다가(1단계), 나중에 다시 돌아와 정답으로 고쳐 제출해도(5단계), 화면엔 "정답"으로 표시되지만 DB·통계상으로는 여전히 "오답 1회"로 집계된다. 반대의 경우(정답→오답으로 바꿔 제출)도 동일하게 최초값이 유지된다.

이 자체가 버그는 아니다 — GEPv30-012 6항("별도 복습 세션에서 다시 푼 경우는 새로운 이벤트로 저장")의 취지상 "같은 세션 내 답 정정은 카운팅 대상이 아니다"로 해석 가능한 설계이기 때문이다. 다만 **계약 문서가 "같은 세션 내에서 답을 바꾼 경우 화면 표시와 실제 집계가 달라질 수 있다"는 점을 명시하지 않고 있어**, 사용자 입장에서는 "분명히 고쳐서 냈는데 왜 오답으로 집계되지" 하는 혼란이 생길 수 있는 지점이다.

## 6. 판단 및 건의

- **재풀이(recordedSet 리셋 후 새 세션) 카운팅 자체는 정상 동작한다.** GEPv30-119 v1.1 결정②("3초 룰로 바꾸기 전 실제 문제 있는지 먼저 검증")에서 우려했던 "재풀이가 카운트 안 된다"는 문제는 **이번 시나리오 범위에서는 재현되지 않았다.**
- 따라서 **"3초 이내 연속 클릭 차단" 방식으로의 변경은 불필요하다고 판단한다.** 오히려 도입 시 "같은 세션 내 중복 클릭 방지"(계약 5항)가 깨질 위험만 커진다.
- 5절에서 발견한 "표시값과 집계값 불일치"는 별개 이슈이며, GEPv30-012에 "같은 세션 내 답 정정 시 최초 제출만 집계됨"이라는 조항을 **명문화**하는 것으로 충분하다고 본다 — 로직 자체를 바꿀 필요는 없어 보인다.
- 최종 판단(계약 개정 여부, 조항 추가 여부)은 지시서 원문대로 조대표 결정 사항으로 남긴다.

## 7. 미검증 사항 (라이브 테스트 필요)

- 위 추적은 `Question.jsx`(서비스 A/B) 1개 파일 기준이다. `ChallengeMode.jsx`·`MockExamQuiz.jsx`·`WrongReview.jsx`·`miniMockService.js`는 각각 별도 가드 구현이라 **동일하게 동작한다는 보장이 없다.** 해당 서비스들이 2~5단계로 개방될 때 이 문서와 동일한 방식으로 개별 검증이 필요하다.
- 실제 Supabase `attempts` 테이블을 조회한 라이브 확인은 하지 못했다. 코드 추적 결론과 실제 브라우저 동작이 다를 가능성(예: React state batching, 네트워크 실패 시 재시도 로직 등 예상 못한 변수)을 배제할 수 없어, 조대표 또는 실계정 보유자의 1회 재현 확인을 권장한다.
