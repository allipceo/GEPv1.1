# GEPv30-140 틀린문제 기능개선 — 전체 디버깅 내역 종합정리 및 재검토 자료

**문서 번호:** GEPv30-140 | **작성일:** 2026-08-20 | **작성자:** 고팀장 (Claude Code) | **상태:** 재검토용 종합 정리 — 추가 코딩 보류
**대상 범위:** GEPv30-135 ~ GEPv30-139 (틀린문제 기능개선 1~3차) 전체
**작성 계기:** 조대표 — "점점 코드가 누더기 걸레가 되고 있는 느낌입니다. 이번 틀린문제 고치기 고도화에서 이루어졌던 디버깅 내용을 모두 정리해서... 전체적인 관점에서 재검토 해야겠습니다."

## 1. 원래 계획 — 무엇을 하려고 시작했는가

GEPv30-135(검토)~136(계획 확정)에서 합의된 범위는 명확했다.

- 틀린문제 복습이 선택형(MCQ)에만 되고 진위형(OX)엔 전혀 안 되던 것을 통합
- 세부과목 기준, 틀린횟수 기준 복습 모드 신설
- 대상 파일 6개 내외, RPC 1개 확장

**이 원래 계획 자체는 크지 않았다.** 문제는 이 범위를 구현하는 과정에서, 그동안 한 번도 실사용 검증되지 않았던 OX 관련 기존 코드 경로들이 연쇄적으로 열리면서 예상 못한 결함이 계속 드러났다는 것이다.

## 4. 왜 이렇게 많이 나왔는가 — 근본 패턴

9건 중 6건(D4~D9)이 **오늘 하루** 조대표의 실사용 테스트 중에 나왔다. 우연이 아니라 구조적인 이유가 있다.

1. **OX 기능(Phase 4)은 "한 번 순차로 풀기"만 실사용 검증되어 있었다.** 재도전(retry), 이어풀기(resume), 통합 복습에서의 OX 처리는 이번에 처음으로 실제 로그인 사용자가 깊게 사용한 경로였다.
2. 그 결과 **오래전부터 있었지만 한 번도 실행되지 않았던 코드**(`loadProgress` 미호출, `questionRaw: null` 고정, `subject` 파라미터 누락)가 이번에 처음 노출됐다. 즉 "새로 만들다가 망가뜨린 것"이 아니라 **"원래도 없었거나 끊어져 있었는데, 이번에 처음 실사용하면서 드러난 것"**이 대부분이다(D5, D8, D9가 이 유형).
3. 다만 조대표 지적대로 **파일 수·커밋 수가 짧은 시간에 누적되며 전체 그림을 파악하기 어려워진 것은 사실**이다 — 이번 문서가 그 전체 그림을 다시 보여주기 위한 것이다.

## 6. 솔직한 코드 품질 평가 — 무엇이 진짜 취약한가

조대표의 "누더기" 지적에 대해 방어하지 않고 있는 그대로 짚는다.

### 6-1. `ChallengeMode.jsx`가 두 가지 서로 다른 모드를 한 파일에서 처리한다

L2-F(세부과목만 필터) 흐름과 L2-D(세부과목+유형+정확한횟수 필터) 흐름이 `subjectFilter`/`sourceFilter`/`exactCount` 3개의 `null` 가능 필터로 한 컴포넌트에 겹쳐 있다. 지금은 "값이 없으면 무시"로 안전하게 설계했지만, **필터가 하나 더 늘어나면 이 패턴은 무너진다.** 두 모드를 별도 컴포넌트로 분리하거나, 공통 로직만 훅으로 뽑아내는 리팩토링이 조만간 필요하다.

### 6-2. `attempts.subject`의 저장 규약이 애초에 통일되어 있지 않다

MCQ는 한글 라벨(`법령`)로, OX는 짧은 키(`law`)로 저장된다 — 이게 D3, D5의 공통 뿌리다. 지금은 **표시할 때마다 매핑 테이블로 정규화**하는 방식으로 땜질했는데, 저장 시점부터 하나의 규약으로 통일하지 않는 한 이런 유형의 버그는 앞으로도 반복될 가능성이 높다.

### 6-3. `progress` 테이블이 서비스마다 다른 의미로 재활용되고 있다

`current_index` 컬럼 하나를 examStore, oxService가 각자 다른 의미로 써왔고(이번엔 "라운드 번호"에서 "재개 인덱스"로 의미를 바꿈), OX 쪽은 그 값을 실제로 읽는 코드가 아예 없었다(D9). **"저장은 했는데 아무도 읽지 않는 코드"가 존재했다는 것 자체가, 이 기능이 만들어질 때 종단 간(end-to-end) 검증 없이 커밋된 적이 있다는 신호다.**

### 6-4. 긍정적인 부분

- RPC·데이터 레이어는 이번에 실측 SQL로 여러 번 교차검증했고 지금은 신뢰할 수 있는 상태(§3의 D1, D3, D5는 전부 SQL로 재확인 완료)
- 각 수정이 "값이 없으면 기존 동작 그대로" 원칙으로 조건부 확장되어, L2-F(기존 통합 오답 복습)는 한 번도 깨지지 않고 지금까지 유지됨
- 발견된 문제 전부가 문서화·백필·재검증까지 완료된 상태 — 미완료 수정은 없음

## 7. 재검토 결정이 필요한 사항

| 옵션 | 내용 | 장단점 |
|---|---|---|
| **A. 현 상태로 로그인 검증 진행 후 병합** | 지금까지 발견된 9건 모두 조치·검증 완료 상태이므로 그대로 진행 | 빠름. 다만 §6의 구조적 취약점은 남는다 |
| **B. `attempts.subject` 저장 규약 통일 리팩토링 선행** | OX도 한글 라벨로 저장하도록 데이터 모델 정리 후 병합 | 근본 원인 제거. 단, 기존 데이터 마이그레이션 범위가 커짐 |
| **C. `ChallengeMode.jsx` L2-F/L2-D 분리 리팩토링 선행** | 두 모드를 별도 컴포넌트로 분리 후 병합 | 향후 확장에 안전. 단, 지금 당장 기능엔 영향 없음 |
| **D. 우선 병합하고 B·C는 별도 세션의 기술부채 정리 작업으로 예약** | 기능은 현재도 정상 동작하므로 분리해서 진행 | 조대표가 "재검토"를 원하는 취지와는 다소 거리 |

고팀장 의견: **A로 로그인 검증까지는 진행하되, B·C는 별도 GEPv30 번호로 기술부채 정리 작업을 예약**하는 것을 권장한다. 지금 상태는 기능적으로 정상이고 전부 실측 검증되었으나, §6의 두 가지 구조적 취약점은 방치하면 다음 기능 추가 때 같은 유형의 버그를 반복시킬 가능성이 높다.
