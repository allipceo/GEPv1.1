# GEPv30-008 1단계 서비스 단계별 개발계획

## 1. 개발 목표

GEP V3.0 1단계 서비스의 목표는 2026년 9월 록토코리아 직원 대상 파일럿 테스트에 사용할 수 있는 기초 서비스를 완성하는 것이다.

1단계 서비스는 다음 두 가지 문제풀이 서비스를 제공한다.

1. 서비스 A: 실제 출제 기출문제를 회차와 문제 순서대로 제공
2. 서비스 B: 10년치 기출문제를 과목별로 분류하여 랜덤 제공

단, 이 서비스의 핵심 가치는 단순 문제 제공이 아니다. 사용자가 문제를 풀 때마다 오늘의 학습량, 누적 정답률, 과목별 취약도, 반복 오답 상태를 확인하고 자신의 현재 위치를 깨닫게 만드는 것이다.

## 2. 개발 운영 원칙

이번 개발은 다음 방식으로 진행한다.

1. 서비스 시나리오를 먼저 확정한다.
2. 구현은 레고블록 단위로 나눈다.
3. 각 Phase 종료 시 승인 게이트웨이를 둔다.
4. 게이트웨이에서는 레드팀 관점으로 비판 점검한다.
5. 문제가 발견되면 해결 전까지 다음 Phase로 넘어가지 않는다.
6. 같은 기술 문제를 20분 이상 해결하지 못하면 중단하고 대표님에게 보고한다.
7. 모든 기획, 결정, 점검, 오류, 수정 결과는 `DOCS/GEPv30-XXX-파일제목` 형식으로 기록한다.

## 3. 전체 Phase 구성

1단계 개발은 다음 8개 Phase로 진행한다.

1. Phase 0: 기준선 점검
2. Phase 1: 서비스 시나리오 확정
3. Phase 2: 데이터와 카운팅 계약 확정
4. Phase 3: 가입 승인 블록 구현
5. Phase 4: 서비스 A 구현
6. Phase 5: 서비스 B 구현
7. Phase 6: 통계와 반복 오답 블록 구현
8. Phase 7: 관리자, 초기화, 파일럿 배포 준비

## 4. Phase 0 기준선 점검

### 4.1 목표

현재 작동 중인 GEP V2.0 앱, GitHub 원천 저장소, DB, 백엔드, 문제 데이터를 개발 기준선으로 확정한다.

### 4.2 작업

1. 현재 로컬 소스 빌드 확인
2. 배포 앱과 로컬 소스의 UI 일치 여부 확인
3. Supabase 연결 구조 확인
4. 기존 사용자, 풀이 기록, 통계 관련 테이블 확인
5. 23회부터 31회까지 문제 데이터 확인
6. 서비스 A와 B에서 재사용할 기존 문제풀이 로직 확인
7. 변경 금지 파일과 재사용 대상 파일 구분

### 4.3 산출물

1. 기준선 점검 보고서
2. 재사용 대상 목록
3. 변경 금지 영역 목록
4. 기존 DB 구조 요약

### 4.4 게이트웨이

다음 조건을 만족해야 Phase 1로 이동한다.

1. 로컬 빌드가 성공한다.
2. 문제 데이터 범위가 확인된다.
3. 기존 카운팅 구조의 재사용 가능성이 확인된다.
4. 현재 앱에서 깨뜨리면 안 되는 기능이 명확히 정리된다.

## 5. Phase 1 서비스 시나리오 확정

### 5.1 목표

파일럿 사용자가 실제로 경험할 서비스 흐름을 문장으로 확정한다.

### 5.2 작업

다음 시나리오를 확정한다.

1. 신규 사용자 가입 승인 요청
2. 운영자 승인
3. 승인 사용자 로그인 또는 접근
4. 서비스 A 순차 기출 풀이
5. 서비스 B 과목별 랜덤 풀이
6. 답안 제출 후 정오답 확인
7. 오늘 통계 확인
8. 누적 통계 확인
9. 과목별 통계 확인
10. 틀린 문제 다시 풀기
11. 반복 오답 문제 다시 풀기
12. 사용자 카운팅 초기화
13. 운영자 카운팅 초기화

### 5.3 산출물

1. 1단계 사용자 시나리오 문서
2. 운영자 시나리오 문서
3. 화면 흐름 초안

### 5.4 게이트웨이

다음 조건을 만족해야 Phase 2로 이동한다.

1. 각 시나리오에 시작 조건, 사용자 행동, 시스템 반응, 저장 데이터, 종료 조건이 있다.
2. 대표님이 1단계 포함 범위와 제외 범위를 승인한다.
3. 시나리오에 없는 기능은 개발하지 않는다는 원칙이 확인된다.

## 6. Phase 2 데이터와 카운팅 계약 확정

### 6.1 목표

답안 제출 1건이 어떻게 저장되고, 그 기록에서 모든 통계가 어떻게 계산되는지 확정한다.

### 6.2 작업

1. 사용자 식별 기준 확정
2. 승인 상태값 확정
3. 답안 제출 이벤트 필드 확정
4. 오늘 전체 통계 계산식 확정
5. 오늘 과목별 통계 계산식 확정
6. 누적 전체 통계 계산식 확정
7. 누적 과목별 통계 계산식 확정
8. 문제별 오답 횟수 계산식 확정
9. N회 이상 반복 오답 필터 기준 확정
10. 카운팅 초기화 방식 확정

### 6.3 산출물

1. 데이터 계약 문서
2. 카운팅 계산식 문서
3. DB 변경 필요 여부 보고서
4. 레드팀 테스트 케이스 초안

### 6.4 게이트웨이

다음 조건을 만족해야 Phase 3으로 이동한다.

1. 모든 통계가 답안 제출 이벤트에서 재계산 가능하다.
2. 서비스 A와 B가 같은 답안 제출 로직을 사용할 수 있다.
3. 초기화 후에도 기록 추적이 가능하다.
4. 기존 DB와 충돌하지 않는다.

## 7. Phase 3 가입 승인 블록 구현

### 7.1 목표

실명과 전화번호 기반 승인 요청 및 운영자 승인 구조를 구현한다.

### 7.2 작업

1. 가입 승인 요청 화면 구현
2. 실명과 전화번호 입력 검증
3. 승인 대기 상태 처리
4. 운영자 승인 처리
5. 승인 사용자만 문제풀이 진입 가능하도록 접근 제어
6. 승인, 거절, 보류 상태 표시

### 7.3 산출물

1. 가입 승인 화면
2. 운영자 승인 기능
3. 승인 상태별 접근 제어
4. 테스트 결과 기록

### 7.4 게이트웨이

다음 조건을 만족해야 Phase 4로 이동한다.

1. 미승인 사용자가 기록되는 문제풀이를 할 수 없다.
2. 승인된 사용자만 서비스 A와 B로 진입 가능하다.
3. 승인 상태가 새로고침 후에도 유지된다.
4. 승인 처리 기록이 남는다.

## 8. Phase 4 서비스 A 구현

### 8.1 목표

실제 출제 기출문제를 회차와 문제 순서대로 제공하는 서비스를 구현한다.

### 8.2 작업

1. 서비스 A 진입 화면 구현
2. 회차 선택 또는 기본 순차 시작 방식 확정
3. 실제 출제 순서 문제 로딩
4. 답안 선택
5. 정오답 표시
6. 공통 답안 제출 이벤트 저장
7. 다음 문제 이동
8. 이어풀기 기준 확인

### 8.3 산출물

1. 서비스 A 화면
2. 순차 문제 공급 로직
3. 답안 제출 이벤트 연결
4. 서비스 A 테스트 결과

### 8.4 게이트웨이

다음 조건을 만족해야 Phase 5로 이동한다.

1. 문제 순서가 실제 기출 순서와 일치한다.
2. 답안 제출 시 정오답이 정확하다.
3. 풀이 이벤트가 누락 없이 저장된다.
4. 오늘 통계와 누적 통계의 원천 이벤트가 생성된다.

## 9. Phase 5 서비스 B 구현

### 9.1 목표

10년치 기출문제를 과목별로 분류하고, 선택 과목에서 랜덤으로 문제를 제공하는 서비스를 구현한다.

### 9.2 작업

1. 서비스 B 진입 화면 구현
2. 과목 선택 UI 구현
3. 선택 과목 문제 풀 구성
4. 랜덤 문제 제공
5. 답안 선택
6. 정오답 표시
7. 공통 답안 제출 이벤트 저장
8. 다음 랜덤 문제 이동

### 9.3 산출물

1. 서비스 B 화면
2. 과목별 문제 풀 로직
3. 랜덤 문제 공급 로직
4. 서비스 B 테스트 결과

### 9.4 게이트웨이

다음 조건을 만족해야 Phase 6으로 이동한다.

1. 선택한 과목의 문제만 제공된다.
2. 랜덤 제공이 문제 데이터 범위를 벗어나지 않는다.
3. 서비스 A와 같은 답안 제출 로직을 사용한다.
4. 과목별 카운팅 이벤트가 정확히 생성된다.

## 10. Phase 6 통계와 반복 오답 블록 구현

### 10.1 목표

사용자가 자신의 현재 위치와 취약점을 즉시 알 수 있도록 핵심 통계를 구현한다.

### 10.2 작업

1. 오늘 전체 풀이 수, 정답 수, 정답률 표시
2. 오늘 과목별 풀이 수, 정답 수, 정답률 표시
3. 누적 전체 풀이 수, 정답 수, 정답률 표시
4. 누적 과목별 풀이 수, 정답 수, 정답률 표시
5. 문제별 오답 횟수 계산
6. 2회 이상 오답 문제 목록
7. 3회 이상 오답 문제 목록
8. 4회 이상 오답 문제 목록
9. 과목별 N회 이상 오답 필터
10. 틀린 문제 다시 풀기 연결

### 10.3 산출물

1. 통계 화면 또는 통계 패널
2. 반복 오답 목록
3. 과목별 반복 오답 필터
4. 오답 다시 풀기 진입점
5. 통계 검증 결과

### 10.4 게이트웨이

다음 조건을 만족해야 Phase 7로 이동한다.

1. 화면 통계와 DB 이벤트 계산 결과가 일치한다.
2. 2회, 3회, 4회 이상 오답 필터가 정확히 작동한다.
3. 서비스 A와 B의 풀이가 하나의 누적 통계로 합산된다.
4. 반복 오답 이력이 사용자가 다시 맞혀도 사라지지 않는다.

## 11. Phase 7 관리자, 초기화, 파일럿 배포 준비

### 11.1 목표

파일럿 운영에 필요한 관리자 기능, 카운팅 초기화, 배포 전 점검을 완료한다.

### 11.2 작업

1. 사용자 목록 확인
2. 승인 상태 확인
3. 사용자별 풀이 수 확인
4. 사용자별 정답률 확인
5. 사용자별 반복 오답 현황 확인
6. 사용자 카운팅 초기화
7. 운영자 카운팅 초기화
8. 초기화 기록 저장
9. 모바일 화면 점검
10. 파일럿 배포 체크리스트 작성

### 11.3 산출물

1. 관리자 확인 화면
2. 카운팅 초기화 기능
3. 초기화 기록
4. 파일럿 배포 체크리스트
5. 최종 레드팀 점검 결과

### 11.4 게이트웨이

다음 조건을 만족해야 파일럿 배포로 이동한다.

1. 운영자가 사용자를 승인하고 관리할 수 있다.
2. 사용자가 본인 카운팅을 초기화할 수 있다.
3. 운영자가 특정 사용자 카운팅을 초기화할 수 있다.
4. 초기화 후 화면 통계가 정확하다.
5. 초기화 기록이 남는다.
6. 모바일과 웹에서 주요 시나리오가 모두 통과된다.

## 12. 레드팀 점검 방식

각 Phase의 게이트웨이에서는 다음 방식으로 점검한다.

1. 정상 사용자가 정상 흐름을 완료할 수 있는가?
2. 비정상 사용자가 우회할 수 있는가?
3. 새로고침, 뒤로가기, 중복 클릭으로 기록이 깨지는가?
4. 화면 통계와 실제 이벤트 기록이 일치하는가?
5. 사용자가 오해할 만한 문구나 화면 흐름이 있는가?
6. 모바일에서 실제 수험생이 불편 없이 풀 수 있는가?
7. 다음 Phase로 넘어가면 되돌리기 어려운 문제가 있는가?

레드팀 점검에서 카운팅 오류가 발견되면 무조건 게이트웨이를 통과하지 못한 것으로 본다.

## 13. 20분 룰

다음 문제는 20분 이상 해결되지 않으면 즉시 중단하고 대표님에게 보고한다.

1. 빌드 실패
2. 배포 실패
3. DB 연결 오류
4. 답안 이벤트 저장 실패
5. 카운팅 불일치
6. 승인 상태 불일치
7. 초기화 오류
8. 재현 가능한 화면 오류

보고 내용은 다음 형식으로 남긴다.

1. 발생 Phase
2. 증상
3. 재현 절차
4. 시도한 해결 방법
5. 확인한 로그
6. 현재 의심 원인
7. 외부 기술자문이 필요한 지점

## 14. 채팀장 실행 기준

채팀장은 다음 기준으로 개발을 진행한다.

1. 대표님 승인 없이 Phase 범위를 넓히지 않는다.
2. 시나리오에 없는 기능은 만들지 않는다.
3. 기존 작동 앱의 좋은 구조는 최대한 재사용한다.
4. 카운팅 로직은 중복 구현하지 않는다.
5. 서비스 A와 B는 공통 답안 제출 로직을 사용한다.
6. 통계는 이벤트 로그 기준으로 검증한다.
7. 막힌 문제는 20분 룰에 따라 보고한다.
8. 각 Phase 종료 시 문서와 테스트 결과를 남긴다.

## 15. 결론

GEP V3.0 1단계 개발은 다음 순서로 진행하는 것이 가장 효과적이다.

**기준선 점검 → 시나리오 확정 → 데이터 계약 확정 → 가입 승인 → 서비스 A → 서비스 B → 통계와 반복 오답 → 관리자와 초기화 → 파일럿 배포**

이 방식은 대표님의 개발 철학인 탑다운, 레고블록, 서비스 시나리오 우선, 철저한 기록유지를 모두 반영하면서도 개발 속도를 유지할 수 있는 절차이다.
