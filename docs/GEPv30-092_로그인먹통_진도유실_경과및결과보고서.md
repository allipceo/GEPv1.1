## 2. 경과 요약 (원인 규명 과정)

당초 계획서 단계에서는 원인을 "로그아웃 직후 강제 풀 리로드(`window.location.href`)가 Navigator LockManager 잠금 해제 타이밍과 겹친다"로 추정했다. 이를 코드 수정(`navigate()`로 교체) 후 즉시 실계정으로 재현 테스트를 했으나, **로그아웃 → 재로그인 시 여전히 로그인이 10초간 응답 없이 멈추는 현상이 재현됨**을 확인했다. 즉, 최초 가설은 원인의 일부였을 뿐 근본 원인이 아니었다.

이에 브라우저 `navigator.locks.query()` API로 실제 잠금 상태를 직접 조회하여 `lock:sb-xnmjprtodyonqzsqxxja-auth-token`이 **exclusive 상태로 영구히 held**되어 있음을 실측 확인했고, `@supabase/auth-js`(`node_modules/@supabase/auth-js/dist/main/GoTrueClient.js`, `SupabaseClient.ts`) 소스코드를 직접 추적하여 진짜 원인을 특정했다:

- `onAuthStateChange` 콜백은 GoTrueClient가 **exclusive lock을 쥔 채로** 호출한다.
- `SupabaseClient._getAccessToken()`은 모든 `.from()`/`.rpc()` 호출 시 내부적으로 `this.auth.getSession()`을 호출하며, `getSession()` 역시 같은 lock을 요청한다.
- 기존 `authStore.js`의 `initAuthListener` 콜백은 `onAuthStateChange` 안에서 곧바로 `supabase.from('users').select(...)`, `supabase.rpc(...)`, `syncFromDB()`(내부적으로 `.from('attempts')`)를 호출하고 있었다.
- 결과: 콜백이 lock을 쥔 채 자기 자신이 필요로 하는 같은 lock을 재요청 → **자기 자신과 데드락**. 이 lock은 GoTrueClient의 `lockAcquireTimeout`(10초) 이후 `isAcquireTimeout` 예외로 포기되지만, **먼저 걸려있던 lock 자체는 반납되지 않고 계속 held 상태로 남아** 이후의 모든 로그인 시도가 동일하게 막힌다. 브라우저를 재시작해도 재현되고, 사이트 데이터 삭제만이 이 상태를 리셋한다는 신고 내용과 정확히 일치.

### 검증 중 발견한 별도 이슈 (범위 외, 참고용)

검증 도중 계정 `202504012`의 DB `approval_status`가 세션 중간에 `'pending'`으로 확인되어 `/service-a` 등 승인 필요 라우트에서 "승인 요청이 필요합니다" 화면이 나타난 시점이 있었다. 이는 실제 운영 계정이라 조대표님 측 동시 사용/조작 가능성이 있으며, 본 건(GEPv30-092)의 원인과는 무관하다. 또한 `RequireLogin.jsx`의 승인 게이트가 `isAdmin` 여부를 고려하지 않아 관리자 계정도 승인이 안 되어 있으면 일반 학습 라우트가 막히는 기존 동작을 확인했다 — **이번 지시 범위(로그인 먹통/진도 유실) 밖이라 수정하지 않았으며**, 필요 시 별도 작업으로 진행 여부를 확인 부탁드린다.
