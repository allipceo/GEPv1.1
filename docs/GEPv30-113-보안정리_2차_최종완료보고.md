### 원 지시서와 다르게 처리한 부분 (검증 중 발견, 노팀장 승인받아 반영)

- **STEP A-2 RPC SQL 수정**: 원안의 `reset_at` 컬럼은 실제 스키마에 없고(`new_baseline_at`이 맞음), `actor_type`이 NOT NULL인데 누락되어 있어 그대로 적용 시 즉시 실패. `previous_baseline_at`을 DB에서 직접 캡처하는 방식으로 재작성.
- **STEP A-3 분기 구조**: `countingResetService.js`가 `AdminUsers.jsx`에서 "관리자가 타인 통계 초기화"에도 재사용되고 있어(targetUserId ≠ actorUserId), 무조건 RPC로 치환하면 관리자 기능이 깨짐. self/operator 분기로 수정하되 기존 함수 시그니처·호출부는 그대로 유지(레고블럭 원칙).
- **STEP D 테이블 DROP**: `devices` 테이블에 `attempts.device_id` FK가 걸려 있어 단순 DROP이 실패. 프론트엔드 어디서도 `device_id`를 쓰지 않음을 grep으로 확인 후 CASCADE로 처리(FK 제약만 제거, `attempts` 테이블/데이터 영향 없음).

## 4. 검증 결과 (운영 DB 실측)

| 항목 | 방법 | 결과 |
|------|------|------|
| RPC 정상 동작(정책 삭제 전) | 실제 로그인 세션에서 `reset_counting_baseline()` 호출 | `reset_baseline_at: null → 2026-08-15T16:28:55...`, `reset_events`에 `actor_type='self', previous_baseline_at=null` 정확히 기록 |
| RPC 정상 동작(정책 삭제 후) | 동일 호출 재실행 | 에러 없음 — SECURITY DEFINER가 RLS 우회 확인 |
| 에스컬레이션 차단 검증 | 클라이언트에서 직접 `.update({service_level:5})` 시도 | `data: []`(0행), 재조회 결과 `service_level` 그대로 `1` — 취약점 차단 실증 |
| `gep_is_admin()` 함수 재정의 확인 | `pg_proc.prosrc` 조회 | `gep_admin_emails` 참조 완전히 사라지고 `users.is_admin` 참조로 교체됨 확인 |
| `gep_is_admin()` 런타임 확인 | 브라우저에서 `supabase.rpc('gep_is_admin')` 호출 | `error: null, data: false, status: 200` (테스터3=비관리자, 정확) |
| `pg_policies` 최종 확인 | `users`/`reset_events` 정책 재조회 | `users_self_update`만 제거, `users_admin_select/update`·`users_self_select/insert`·`reset_events_self_*` 전부 정상 유지 |
| 테이블 정리 확인 | `list_tables` | 9개 테이블만 남음(users/attempts/question_stats/progress/reset_events/mock_exam_sessions/mock_exam_attempts/custom_mock_sessions/custom_mock_attempts) — 코드 실사용 테이블과 정확히 일치 |
| Security Advisor | `get_advisors(security)` | 신규 CRITICAL/ERROR 없음. 기존부터 있던 WARN(search_path, anon 실행권한, leaked-password)만 잔존 — 이번 작업과 무관, 범위 밖 |
